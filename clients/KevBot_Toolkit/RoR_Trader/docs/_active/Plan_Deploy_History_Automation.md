# Plan — Keep `deploy_history.json` fresh automatically (board #50)

**Owner:** F · **Status:** Part 1 shipped (regenerated); Part 2 = proposal for M/R
decision (touches release/deploy pipeline → outside F's lane to activate).

## Problem

The Strategy-Health **"By Deploy"** tab buckets pair-rate metrics by deploy
window. It reads deploy timestamps from a static file, `src/deploy_history.json`,
generated by `src/_generate_deploy_history.py` (`git log origin/dev`).

That file is generated **manually** and had not been run since **2026-06-12**
(134 commits, all ≤ 06-12). By 07-26 `origin/dev` had **548** commits in the
window, so every recent deploy window was empty and the tab showed
_"no deploys recorded in window (deploy_history.json may be missing or out of
date)"_ — even for last-14d.

## Why it can't self-heal at runtime or build time

- **Runtime:** the API container has **no git history** — `.dockerignore`
  excludes `.git/`. `_load_deploy_history()` can only read the pre-baked JSON.
- **Build time:** the Dockerfiles `COPY src/` from the build context, which also
  has no `.git/`. The build cannot regenerate it either.
- **Deploy trigger:** merge/push to `dev` → **Railway auto-redeploys**. The JSON
  must therefore be **regenerated and committed BEFORE the merge** so the fresh
  copy is baked into the image.

Net: freshness must be produced at **commit/merge time on a host that has git
history**, not in the container or the image build.

## Part 2 — Never stale again (pick one; M/R to activate)

The script hardening already makes the manual step foolproof and one command:

```bash
cd clients/KevBot_Toolkit/RoR_Trader/src && python3 _generate_deploy_history.py
# then commit src/deploy_history.json
```

The remaining question is only **where that runs automatically**. Options,
low-risk → most-durable:

### Option A (recommended, zero new infra) — fold into the release/train SOP

Every dev deploy already goes through the **train / Release (R)** flow
(`/release-brief`, `Deploy_Log.md`). Add one mechanical pre-merge step to that
checklist:

> Before merging the train branch to `dev`: run
> `python3 src/_generate_deploy_history.py`, and if `src/deploy_history.json`
> changed, commit it onto the train branch (`chore: refresh deploy_history`).

- **Pros:** no infra, no double-deploys, runs on the exact host/moment that has
  git history, is already a checkpoint a human/R passes through every deploy.
- **Cons:** still a human step (but a single, documented, checklist-gated one —
  and the auto-fetch removes the "did I fetch first?" footgun).
- **To activate:** R/M adds the line to the release-brief checklist / train SOP.
  (F can supply the exact wording; editing R's skill is R/M's call.)

### Option B (durable, server-side) — GitHub Action on push to `dev`

A workflow regenerates the JSON server-side and commits it back. **Requires
verifying Railway `watchPatterns` do NOT include `src/deploy_history.json`** so
the write-back commit does not trigger a second redeploy (docs reference
`watchPatterns=[]` on at least one service — must be confirmed per service
before enabling). Drop-in workflow (place at repo root `.github/workflows/`,
only M/R should enable — it writes to `dev`):

```yaml
name: refresh-deploy-history
on:
  push:
    branches: [dev]
    paths-ignore: ['clients/KevBot_Toolkit/RoR_Trader/src/deploy_history.json']
jobs:
  refresh:
    runs-on: ubuntu-latest
    permissions: { contents: write }
    steps:
      - uses: actions/checkout@v4
        with: { ref: dev, fetch-depth: 0 }   # full history; git available here
      - name: Regenerate
        run: |
          cd clients/KevBot_Toolkit/RoR_Trader/src
          python3 _generate_deploy_history.py --ref dev --no-fetch
      - name: Commit if changed
        run: |
          cd clients/KevBot_Toolkit/RoR_Trader
          if ! git diff --quiet src/deploy_history.json; then
            git config user.name  'deploy-history-bot'
            git config user.email 'bot@users.noreply.github.com'
            git commit -am 'chore: refresh deploy_history.json [skip ci]'
            git push
          fi
```

- **Pros:** truly hands-off; covers GitHub-UI merges (which local hooks miss).
- **Cons:** commits back to `dev` (needs `watchPatterns` check to avoid a second
  Railway deploy); the just-pushed commit is one behind (excludes the bot commit
  itself — acceptable for window bucketing); **no CI infra exists today**, so
  this is net-new pipeline surface that is M/R's to own, not F's.

### Option C (local pushes only) — pre-push git hook

A `.githooks/pre-push` that, on a push whose remote ref is `dev`, regenerates
against the local tip (`--ref <local-sha> --no-fetch`) and blocks the push if the
JSON is stale so it gets committed first. **Not recommended here:** the repo is a
shared monorepo with many worktrees/agents; a blocking pre-push hook affects
every subproject's pushes, and most dev deploys land via the GitHub PR button
(server-side), which a local hook never sees. Listed for completeness.

## Recommendation

Ship Part 1 (done). For Part 2, adopt **Option A** immediately (one SOP line,
zero risk), and consider **Option B** later if/when GitHub Actions is stood up
for this repo and `watchPatterns` are confirmed. The script now supports both
(`--ref` / `--no-fetch` for the CI path; bare auto-fetch for the SOP path).
